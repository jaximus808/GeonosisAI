- **TDM-55 camera streaming = JPEG frames over one WebSocket per viewer (`jpeg-ws/1`, `services/robot-client/src/rdf_robot_client/stream.py`), exposed through a cloudflared quick tunnel (no account), with ack pacing and HMAC tokens minted only for the current task claimant. It is not WebRTC tonight.**
  - **Why:**
    - The hard part is getting from an office Jetson to the public internet. A quick tunnel is outbound-only HTTPS and falls back from QUIC to TCP 443 by itself, so NAT type and UDP filtering at the office or venue don't matter.
    - WebRTC without TURN fails on symmetric NAT, and we have no TURN server: Fly is on hold and there are no TURN credentials. aiortc would also software-encode VP8/H.264 on the Jetson CPU, and it still needs a reachable signalling server.
    - Each frame is acked after it is drawn, with at most 2 frames in flight per camera. A slow link loses fps instead of building a backlog, so latency stays bounded for teleop.
    - Ping/pong syncs the robot's monotonic clock to the browser, so the badge shows real capture-to-screen latency.
    - Measured on the laptop (synthetic cameras, 424 px, 20 fps, both cameras, laptop -> Cloudflare LAX -> laptop):
      - probe: p50 38–40 ms, p95 77–92 ms;
      - Chrome capture->screen: p50 50–60 ms;
      - local without the tunnel: about 7–12 ms.
      - These leave out the camera's own exposure and USB time (about one frame). True glass-to-glass on the Jetson is a checklist step.
  - **Auth:**
    - The browser proves its SpacetimeDB identity (SpacetimeDB `GET /v1/identity/{id}/verify`).
    - The orchestrator (`POST /stream/token`, `stream_api.py`, reached through the web proxy `/api/tdm55/stream-token`) mints a token only if that identity's contributor is the assignee of a `claimed` task with a live lease.
    - The token is scoped to the task's robot, lasts 60 s and never outlives the lease by more than 10 s. The browser refreshes it at half-life, and the robot closes the socket with code 4001 when it lapses.
    - Shared key: `RDF_STREAM_TOKEN_SECRET`. The TDM-47 MJPEG server has no auth and stays on localhost.
  - **Fallback:** after 3 failed WebSocket opens, the browser polls `/snapshot/<cam>.jpg?token=` at about 5 fps and keeps retrying the WebSocket every 30 s.
  - **Decided by:** TDM-55 worker.
  - **Revert / alternatives, quickest first:**
    1. Tunnel flaky: run `stream serve --tunnel none` on the LAN and set `RDF_STREAM_URL=ws://<jetson>:8091/ws/cameras` on the orchestrator. That works for the venue phone if it is on the same network.
    2. Swap the tunnel provider, e.g. ngrok once `NGROK_AUTHTOKEN` is set: `ngrok http 8091` and put its `wss://` URL in `RDF_STREAM_URL`. The protocol and auth stay the same.
    3. A cloudflared named tunnel with a Cloudflare account gives a stable hostname.
    4. WebRTC later: add `transport: "webrtc"` to `robot.camera_config_json.stream` and signal over this same authenticated WebSocket (offer/answer messages). `CameraStreamClient` stays the fallback.
    5. Bandwidth-bound (about 2 Mbit/s per camera at 424 px / q70): `--width 320 --fps 15`.
